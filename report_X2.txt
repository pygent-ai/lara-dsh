## 五、两个已知点核验

### 1) `scheduler/store.py` vs `dispatch/store.py` 的“队列语义”

**结论：不构成可直接合并的重复实现，该保留；但 `dispatch` 与 `sessions/collaboration` 之间有一处真重复。**

- AST 两两比较中，两文件之间 **没有任何函数对达到 0.75**。
- 语义层：
  - `scheduler/store`：`submissions → tasks → runs` 三表；`claim_due_tasks`（优先级排序 + `BEGIN IMMEDIATE` + 逐行条件 UPDATE）、`claim_task`、`release_task` 带 `lease_id/lease_expires_at` 租约；`prompt_hash` 只在任务创建时落库，`daemon.py:381` 用于执行前校验 prompt 未被篡改。
  - `dispatch/store`：只有 `dispatch_items` 单表 + `migrate_legacy_automations`；**没有任何 claim/release/next_run 实现**，`owner_id/lease_until_epoch` 只是预留列。幂等提交（`INSERT` 捕获 `IntegrityError` + 按 `submission_id` 回读 + `fingerprint` 冲突报错）比 scheduler 的 `INSERT OR IGNORE`（`store.py:369-372`）更严格。
- 唯一实质重复是**幂等指纹**的同一个辅助函数：`_fingerprint@dispatch/store.py:18` 与 `_fingerprint@orchestration/session_collaboration.py:307` 逐字相同，应该合并（不是与 scheduler 合并）。
- 真正“同构但不同粒度”的租约状态机是 `SchedulerStore.claim_due_tasks@…:584` vs `SessionCollaborationStore.claim_messages@sessions/collaboration.py:235`：前者按到期时间+优先级批量认领任务，后者按目标会话+过期回收认领消息，SQL 条件与回收策略不同 → **保留两套**，强行合并会把两种队列语义耦死。
- 状态枚举 `DispatchItemState@dispatch/models.py:14` 与 `CollaborationState@sessions/collaboration.py:15` 值域重叠但集合不同（前者有 `claimed/cancelled`，后者有 `preparing/starting`）→ **保留**。

### 2) `scheduler/message.py` vs `runtime/reminders/rendering.py` 的时间块

- 时间行本身已共用 `core/timefmt.format_current_time_line`，无第二份 `strftime`。
- **仍残留逐字重复片段**：
  - `scheduler/message.py:39`：`Prompt(f"  {format_current_time_line(timestamp)}").wrap("time")`
  - `runtime/reminders/rendering.py:26-28`：`Prompt(f"  {format_current_time_line(timestamp)}").wrap("time")`
  → 建议在 `timefmt` 增加 `render_time_block(moment) -> Prompt`，两端直接调用。
- 顺带发现**语义漂移**：`message.py:37` 先把时间 `astimezone(timezone.utc)`，`rendering.py:24` 用 `datetime.now().astimezone()`（本地时区）。同一个 `<time>` 信封在两条路径可能显示不同时区（`%Z` 不同），这不是单纯重复，而是行为不一致，合并时间块 helper 时应一并统一。
- 缩进：`message.py:19 _indent` 与 `Prompt._indent_body`（`core/prompt.py:87`）重复；`rendering.py` 则直接用 `Prompt.wrap(indent="  ")`，两条路径的缩进实现也不统一。

## 六、Top 清单（按“合并收益 / 漂移风险”排序）
