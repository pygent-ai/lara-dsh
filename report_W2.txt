# 死代码验证 W2（只读，未修改任何文件）

`git status --porcelain` 与开始时一致，仍只有既有的 `report_V1..V4.txt`（未跟踪）。全程只做 AST / rg / 人工读码 / `git log -S`。

## 调查方法与前提

1. AST 抽取 14 个目标文件的全部模块级函数/类/方法/模块常量（公开符号约 **184 个**）。
2. 对 `src/lara` + `src/standard_agent` + `tests` + `examples` 建 `Name`/`Attribute`/`import` 索引；对同名方法再做接收者复核（避免把 `session.close()` 误算成 `BashTaskObservations.close()`）。
3. `rg` 全仓复核，含 README/pyproject；对 `.venv` 内同名符号单独排查（`get_task`/`cancel_task`/`wait_idle`/`resumable` 的命中全部是 pygent/mcp 自身符号，与 Lara 无关）。
4. 动态派发专项：`getattr`/`setattr`/字符串方法名/`importlib`/entry points；`service.py` 没有按字符串调用自身方法的分发器。
5. `git log -S` 追溯：绝大多数候选自 `767a413`（“Extract complete agent implementation from lara”）进入本仓后从未被接线；`5a142ff` 只改写了 `send_interrupt` 方法体并新增测试，没有新增生产调用者。

关键背景证据：
- `src/lara/__init__.py:1-8` 明示“原仓的 evaluation / repair / automations / workflows 与 lara_api 服务层已裁剪”。
- `tests/test_import_completeness.py:39-41` 断言 evaluation/repair/automations/workflows 目录不存在。
- `src/lara/runtime/README.md:34` 说 `service.py` 是“session-oriented runtime facade used by API and CLI adapters”，而 API 适配层已不在本仓 —— 这是下面一批“facade-only”死代码的来源，也意味着**删前需确认上游 API 是否仍引用**。
